# Import & Export Center operations

## Supported first-release data types

The versioned server catalog is in `backend/src/ImportExportSchema.php`. It drives template headings, field validation, export columns, and field permission checks.

- Imports and exports: Employees, spouses, children, licenses, Social Insurance records, Hiring Plans, and the Setup reference tables used by HMS.
- Exports only: employee document metadata and contract renewal history.
- Users, roles, permissions, and assignments are excluded from ordinary HR workbooks.
- Files are `.xlsx` only. No CSV path is provided.

Employee-linked records use Employee Number; the PHP API and database batch function resolve it to the internal employee ID. New employees leave Employee Number blank and include a source reference. The result workbook maps the source reference and input row to the number generated by the HMS employee trigger.

Repeated records use these rules: spouse and child by Employee Number + National ID; license by Employee Number + license type + release date + expiry date; Social Insurance by Employee Number; Hiring Plan by project + department + position. A child’s optional spouse name must match one spouse for that employee. Setup records update by case-insensitive exact name; position codes are separately checked for conflicts.

## Runtime and retention

The current local PHP runtime reports `upload_max_filesize=2M` and `post_max_size=8M`; the importer therefore enforces a 2 MiB workbook limit. Increase both PHP settings through the hosting runtime’s approved configuration before raising `ImportExportWorkbook::MAX_FILE_BYTES` and the UI copy. Do not rely on `ini_set()` for multipart upload limits because PHP parses the request before the API runs.

Imports stage rows durably in `import_export_jobs` and `import_export_job_rows`. Each authenticated resume call processes at most 25 rows (the database RPC caps each call at 50). The client can leave and later resume. Successful row writes and row markers commit together; failed rows can be retried without reprocessing successful rows. This runtime has no configured background worker, so processing advances when an authorized user opens/resumes the job.

Exports are recorded and stored in the private `import-export` bucket with a 24-hour job expiry and five-minute signed download links. The current first release builds exports synchronously and caps them at 10,000 records. Larger exports are rejected and need narrower filters. Expired jobs and private objects are deleted in bounded batches when the center is opened; this is opportunistic cleanup, not a scheduled retention worker. Add a scheduled cleanup mechanism before production scale requires guaranteed deletion at a fixed time.

## Workflows deferred pending model-specific design

- Document import is deferred. HMS stores document files in private storage, so accepting metadata alone could create a dangling record. A paired private attachment upload with explicit row references and employee numbers needs a separate workflow and storage validation.
- Contract renewal import is deferred. Renewal history is created through the dedicated renewal function and connected renewal tracker, which enforce contract dates and workflow state. A workbook importer needs a transaction design that preserves those effects; renewal export remains available.
- The first export UI supports all rows matching its current filters (Employee Number for employee-linked data). It does not yet support current-page or selected-record exports, arbitrary field reordering across all filters, or asynchronous large export jobs.
